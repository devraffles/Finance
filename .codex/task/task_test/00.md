# Task - Configuração de Testes e Atualização das Tasks Existentes

## Objetivo

Configurar a infraestrutura completa de testes no monorepo `kwak-finance/` e atualizar **todas as tasks existentes em `@task/`** para incluir etapas obrigatórias de cobertura de testes em cada funcionalidade implementada.

## Contexto obrigatório

Antes de implementar, leia:

- `AGENTS.md`
- `.codex/tasks.md`
- `.codex/rules/general.md`
- `.codex/rules/testing.md` ← criado por esta task
- `prompt-projeto-codex.md`

Não use a pasta `app/` como referência de configuração de testes.

## Stack de testes adotada

| Camada                           | Ferramenta                   | Motivo                                      |
| -------------------------------- | ---------------------------- | ------------------------------------------- |
| Unitário / Integração (backend)  | **Vitest**                   | Suporte nativo a ESM (`"type": "module"`)   |
| Unitário / Integração (frontend) | **Vitest + Testing Library** | Consistência com o backend no monorepo      |
| E2E                              | **Playwright**               | Multi-browser, integração com CI, melhor DX |
| Mock do Prisma                   | **vitest-mock-extended**     | Evita banco real nos testes unitários       |
| Cobertura                        | **@vitest/coverage-v8**      | Nativo ao Vitest, zero config extra         |

## Tarefas

### 1. Instalar dependências de teste

```bash
# Backend
pnpm --filter @kwak-finance/backend add -D vitest @vitest/coverage-v8 vitest-mock-extended

# Frontend
pnpm --filter frontend add -D vitest @vitejs/plugin-react @testing-library/react @testing-library/user-event jsdom @vitest/coverage-v8

# E2E (raiz do monorepo)
pnpm add -D -w @playwright/test
npx playwright install --with-deps
```

### 2. Criar arquivos de configuração

#### `backend/vitest.config.ts`

```ts
import { defineConfig } from "vitest/config";

export default defineConfig({

      provider: "v8",
      reporter: ["text", "lcov"],
```

### 5. Criar `.codex/rules/testing.md` com regras e exemplos

Criar o arquivo `.codex/rules/testing.md` com o conteúdo abaixo. Este arquivo é **leitura obrigatória** para qualquer agente antes de escrever testes.

````markdown
# Regras de Testes — kwak-finance

## Princípios gerais

- Todo código novo deve ter testes. Sem exceção.
- Testes devem ser legíveis como documentação: quem lê o teste deve entender o comportamento esperado sem ver a implementação.
- Prefira muitos testes pequenos e focados a poucos testes grandes e genéricos.
- Nunca use o banco de dados real em testes unitários.
- O comando `pnpm test` deve sempre passar na branch `main`.

---

## Nomenclatura

- Arquivos de teste: `nome-do-arquivo.test.ts` ou `nome-do-arquivo.spec.ts`
- Localização: dentro de `__tests__/` na mesma camada do código testado
- Descreva o comportamento, não a implementação:
  - ✅ `it('deve retornar erro quando o email já está cadastrado')`
  - ❌ `it('testa o método createUser')`

---

## 1. Testes Unitários (Vitest)

Use para: funções puras, schemas Zod, utilitários, lib/auth, transformações de dados.

### Exemplo — validação de schema Zod

```ts
// backend/src/__tests__/unit/schemas/auth.test.ts
import { describe, it, expect } from "vitest";
import { signUpSchema } from "@kwak-finance/backend/schemas/auth";

describe("signUpSchema", () => {
  it("deve aceitar dados válidos", () => {
    const resultado = signUpSchema.safeParse({
      email: "user@example.com",
      password: "Senha@123",
      name: "João Silva",
    });
    expect(resultado.success).toBe(true);
  });

  it("deve rejeitar email inválido", () => {
    const resultado = signUpSchema.safeParse({
      email: "nao-e-um-email",
      password: "Senha@123",
      name: "João Silva",
    });
    expect(resultado.success).toBe(false);
    expect(resultado.error?.issues[0].path).toContain("email");
  });

  it("deve rejeitar senha com menos de 8 caracteres", () => {
    const resultado = signUpSchema.safeParse({
      email: "user@example.com",
      password: "123",
      name: "João Silva",
    });
    expect(resultado.success).toBe(false);
  });
});
```

## 2. Testes de Integração com Prisma mockado (Vitest + vitest-mock-extended)

Use para: services, repositórios, lógica que depende do banco de dados.

**Nunca conecte ao banco real nos testes unitários/integração.**

### Exemplo — service de transações

```ts
// backend/src/__tests__/integration/transaction.service.test.ts
import { describe, it, expect, vi, beforeEach } from "vitest";
import { mockDeep, mockReset } from "vitest-mock-extended";
import { PrismaClient } from "@prisma/client";
import { TransactionService } from "../../services/transaction.service";

const prismaMock = mockDeep<PrismaClient>();

beforeEach(() => {
  mockReset(prismaMock);
});

describe("TransactionService.create", () => {
  it("deve criar uma transação com sucesso", async () => {
    const transacaoFake = {
      id: "1",
      amount: 150.0,
      description: "Supermercado",
      userId: "user-123",
      createdAt: new Date(),
    };

    prismaMock.transaction.create.mockResolvedValue(transacaoFake);

    const service = new TransactionService(prismaMock);
    const resultado = await service.create({
      amount: 150.0,
      description: "Supermercado",
      userId: "user-123",
    });

    expect(resultado).toEqual(transacaoFake);
    expect(prismaMock.transaction.create).toHaveBeenCalledOnce();
  });

  it("deve lançar erro se userId não for fornecido", async () => {
    const service = new TransactionService(prismaMock);

    await expect(
      service.create({ amount: 100, description: "Teste", userId: "" }),
    ).rejects.toThrow("userId é obrigatório");
  });
});
```

## 3. Testes de Componente (Vitest + Testing Library)

Use para: componentes React, formulários, interações do usuário.

### Exemplo — formulário de login

```tsx
// frontend/src/__tests__/components/LoginForm.test.tsx
import { describe, it, expect, vi } from "vitest";
import { render, screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LoginForm } from "../../components/LoginForm";

describe("LoginForm", () => {
  it("deve renderizar os campos de email e senha", () => {
    render(<LoginForm onSubmit={vi.fn()} />);

    expect(screen.getByLabelText(/email/i)).toBeInTheDocument();
    expect(screen.getByLabelText(/senha/i)).toBeInTheDocument();
  });

  it("deve chamar onSubmit com os dados corretos ao submeter", async () => {
    const onSubmit = vi.fn();
    render(<LoginForm onSubmit={onSubmit} />);

    await userEvent.type(screen.getByLabelText(/email/i), "user@example.com");
    await userEvent.type(screen.getByLabelText(/senha/i), "Senha@123");
    await userEvent.click(screen.getByRole("button", { name: /entrar/i }));

    await waitFor(() => {
      expect(onSubmit).toHaveBeenCalledWith({
        email: "user@example.com",
        password: "Senha@123",
      });
    });
  });

  it("deve exibir erro de validação se email estiver vazio", async () => {
    render(<LoginForm onSubmit={vi.fn()} />);

    await userEvent.click(screen.getByRole("button", { name: /entrar/i }));

    expect(await screen.findByText(/email é obrigatório/i)).toBeInTheDocument();
  });
});
```

## 4. Testes E2E (Playwright)

Use para: fluxos completos do usuário — login, cadastro, criação de transação, etc.

### Exemplo — fluxo de autenticação

```ts
// e2e/auth.spec.ts
import { test, expect } from "@playwright/test";

test.describe("Autenticação", () => {
  test("deve fazer login com sucesso e redirecionar para o dashboard", async ({
    page,
  }) => {
    await page.goto("/login");

    await page.getByLabel("Email").fill("user@example.com");
    await page.getByLabel("Senha").fill("Senha@123");
    await page.getByRole("button", { name: /entrar/i }).click();

    await expect(page).toHaveURL("/dashboard");
    await expect(page.getByText(/bem-vindo/i)).toBeVisible();
  });

  test("deve exibir mensagem de erro com credenciais inválidas", async ({
    page,
  }) => {
    await page.goto("/login");

    await page.getByLabel("Email").fill("errado@example.com");
    await page.getByLabel("Senha").fill("senha-errada");
    await page.getByRole("button", { name: /entrar/i }).click();

    await expect(page.getByText(/credenciais inválidas/i)).toBeVisible();
    await expect(page).toHaveURL("/login");
  });
});
```

## O que NÃO fazer

| ❌ Errado                                   | ✅ Correto                                       |
| ------------------------------------------- | ------------------------------------------------ |
| Conectar ao banco real em testes unitários  | Usar `vitest-mock-extended` para mockar o Prisma |
| Usar `any` nos mocks                        | Tipar os mocks com os tipos reais                |
| Testar detalhes de implementação            | Testar comportamento observável                  |
| Um único `describe` com 20 `it` sem relação | Agrupar por funcionalidade/contexto              |
| Ignorar falhas e dar `.skip` sem explicação | Corrigir ou abrir issue documentando             |
| Rodar testes E2E contra produção            | Usar apenas `localhost` ou staging               |

---

## Cobertura mínima esperada

| Camada                                  | Mínimo              |
| --------------------------------------- | ------------------- |
| Schemas / validações                    | 100%                |
| Services / lógica de negócio            | 80%                 |
| Componentes com formulário ou interação | 70%                 |
| E2E por fluxo principal da feature      | 1 teste por feature |
````

```markdown
### Testes obrigatórios para esta task

- [ ] Escrever testes unitários para toda lógica de negócio nova (Vitest)
- [ ] Escrever testes de integração para os endpoints ou server actions criados (Supertest / Vitest)
- [ ] Escrever testes de componente para todo componente novo (Testing Library)
```

#### No **Checklist** de cada task, incluir ao final:

```markdown

- [ ] Ao menos 1 teste E2E cobrindo o fluxo principal
```

## Regras

- Nenhum código de produção pode ser entregue sem ao menos testes unitários cobrindo a lógica principal.
- O banco de dados real **nunca** deve ser usado nos testes unitários — use `vitest-mock-extended` para mockar o Prisma.
- Testes E2E devem rodar contra o ambiente local (`http://localhost:3000`) ou de staging, nunca produção.
- Não commitar snapshots de testes desatualizados.
- O comando `pnpm test` deve sempre passar na branch `main`.
